Mail that lives in Ceph.
No file system. No database.

ShardPost is a mail server written in Go. It keeps mailboxes, messages and its own coordination state directly in Ceph RADOS and serves them over IMAP, JMAP, POP3, LMTP and ManageSieve. Several replicas share one store, and Nauthilus decides who gets in.

The stack

Nauthilus lets them in. ShardPost serves them. Ceph keeps it.

ShardPost is the mailbox and processing layer of a mail system. Internet SMTP, authentication and storage are separate components with their own contracts. This is how they work together, from the app on a phone to the object on a disk.

Storage

Three pools. One namespace per account.

Messages and ordered mailbox metadata map well onto Ceph's object and omap operations, so ShardPost talks to RADOS directly. Index and payload have different needs and get different pools.

ceph.index_pool · replicated

Index

Each account's mailboxes, message entries with envelope and preview, quota, change log, Sieve scripts and full-text index, as omap keys. Many small keys, read and rewritten all the time: replicated, ideally on fast disks.

ceph.data_pool · erasure coded

Data

The message bytes, in chunks of 4 MiB by default. A blob is written once and never changed, so the pool can be erasure coded without overwrites. COPY adds a reference instead of copying bytes.

ceph.system_pool · optional

System

The small, hot store-wide state: admin store, account directory, queues and locks. With its own pool it sits on fast OSDs, apart from the accounts' objects.

Many servers, no central database

Every replica can change every account. Instead of a database server, ShardPost coordinates through RADOS itself, and the order of writes is chosen so that a crash never leaves a broken account.

  • Compare-and-swap on object versions for every change of one object
  • Intents for changes across objects, which the scrub finds without listing the pools
  • Watch and notify to wake IDLE, NOTIFY and push sessions on any server
  • Locks with a time to live for POP3 maildrops, the learning worker and push partitions; leases on job records

Protocols

Every client, one store.

IMAP, POP3 and JMAP read the same index, the same blobs and the same account change log. A message flagged on the phone over JMAP is flagged in the desktop client over IMAP.

IMAP with its modern extensions

ShardPost's own IMAP parser and dispatcher advertise IMAP4rev2 next to IMAP4rev1, with the extensions clients rely on for fast synchronisation, search and sharing.

  • CONDSTORE and QRESYNC, IDLE and NOTIFY, COMPRESS=DEFLATE
  • SORT, THREAD, ESEARCH, full-text search with English and German stemming
  • ACL with shared folders under Shared/ and public folders under Public/
  • QUOTA, METADATA, SPECIAL-USE, OBJECTID, PREVIEW, IMAPSIEVE

JMAP, built in

JMAP is a third front-end on the same store, not a second data store. It covers the RFC 8621 mail model with push, sharing and Sieve, and it is what the native app JMapper Mail is built on.

  • Push over EventSource and Web Push with VAPID, from workers that share 64 partitions
  • Sending through your relay, with delayed sending (FUTURERELEASE) that can be cancelled
  • Shared and public folders as accounts, principals and share notifications (RFC 9670)
  • Quotas, vacation response, blobs and Sieve scripts over JMAP

Operations

Built to be run, not just started.

An admin API with an OpenAPI contract, a command-line client with roles, a manual page for every command group, metrics, traces and structured logs.

Diagnose without guessing

shardpostctl talks to the admin API over a Unix socket inside the server or over mutual TLS. Diagnosis sees metadata only; reading message content is a role of its own.

  • Accounts, aliases, quotas, mailboxes and their consistency
  • Maintenance jobs for repairs, recounts and deletions, also over all accounts
  • An IMAP protocol trace for one account, switched on for a limited time
  • One auth cache flush for every server at once

Move in without your users noticing

shardpostctl migrate imports an account from another IMAP server through a master-user login. UIDs, UIDVALIDITY and MODSEQ stay the same, so clients keep their caches and do not download everything again.

  • Uses CONDSTORE, X-GUID and SAVEDATE when the source offers them
  • Copies Sieve scripts over ManageSieve and keeps Dovecot POP3 UIDLs
  • Runs repeatedly until a run reports few changes
  • Export to a tar archive with a SHA-256 manifest, verify, restore

And more

The parts a real mail system needs.

Sieve and IMAPSieve

A Sieve interpreter with vacation, editheader, duplicate, date, body, imap4flags and more at delivery, ManageSieve to manage scripts, and IMAPSieve on mailbox events.

Learning for spam filters

Moving mail into or out of Junk can feed a classifier such as Rspamd through an allowlisted external program, from a durable queue that survives EXPUNGE and restarts.

Full-text search

Headers, text and HTML parts, file names and attached messages, with English and German stemming and substring search, for IMAP and JMAP.

Quota with rules

Storage and message limits with grace, per-mailbox rules, warning programs at thresholds and an over-quota flag in the user database.

Shared and public folders

Folders shared by ACL, public folders with their own quota and a private \Seen flag per user, in IMAP and JMAP.

Limits per account

Configurable upper bounds for mailboxes, keywords, metadata and shares, so one account cannot grow without end.

Before you start

What ShardPost needs, and what it does not do.

ShardPost is one layer of a mail system. It expects the others to be there, and it says plainly where it stops.

What you need

  • A Ceph cluster, and librados2 of the cluster's version on each server host
  • Linux, in containers or natively with systemd; Kubernetes and Rook are optional
  • Nauthilus for authentication and the canonical account (a static backend exists for tests)
  • An MTA in front that delivers over LMTP, and an SMTP relay for outgoing mail

Get started →

What it does not do

  • Accept internet SMTP or offer a submission port (587/465)
  • Encrypt or compress messages at rest
  • Contacts and calendars, JMAP over WebSocket
  • Search attachment content or CJK text
