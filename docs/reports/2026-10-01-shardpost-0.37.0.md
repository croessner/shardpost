# ShardPost 0.37.0: account directory (scaling stage R1a) and ESORT

Date: 2026-10-01

## Change

First stage of the plan to run ShardPost with millions of accounts: no
RADOS object listing in running paths. A namespace listing visits every
PG of a pool, so its cost grows with all objects in the pool, not with
the namespace. 0.37.0 lays the foundation and makes the listings
visible; later stages replace them.

- **Sorted index primitive** (`model.SortedIndex`, `internal/sortedindex`):
  omap index objects `ix.<name>/<nn>` with a head object (shard count,
  format, reshard phase), paged by `<shard>:<id>` cursor.
- **Account directory** (`~accounts`, 256 shards): an account is listed
  exactly when its registry object exists. The registry is created in
  one place (`casOmapOpAs` at version 0); the entry is written right
  before it. A purge marks the entry `purging` with its job session, so
  no late session or delivery can re-create the account while or after
  it is purged; a new purge phase removes the entry. Repair through
  `shardpostctl account repair`, inspection through
  `shardpostctl account directory`.
- **Grants** to an account being purged are refused (`409
  account_purging`, IMAP `NO [UNAVAILABLE]`).
- `Store.User` refuses the empty name and unknown reserved names.
- **Metric** `imapceph_rados_listings_total{site}` counts every remaining
  listing.
- **Backfill** `shardpost index backfill accounts` (CLI, under a RADOS
  lock), mandatory once after the rollout.
- **IMAP ESORT** (RFC 5267): `SORT … RETURN (MIN MAX ALL COUNT SAVE)`;
  unknown RETURN options are now `BAD` for SEARCH too, SAVE follows
  RFC 5182 exactly.

## Review

Plan: six review rounds by a second model until R1a and R1b were
released. Implementation: three rounds; found and fixed among others a
race between the stale-entry repair and a concurrent account creation,
a purge left `purging` without a restart path, and a grant that a
purged name would have inherited.

## Rollout

1. 0.37.0 rolled out; no error in the logs.
2. After the last 0.36.1 pod had drained: `shardpost index backfill
   accounts` — 33 accounts entered in under one second.
3. Smoke test `hack/directory-smoke.sh` against the live cluster with the
   imaptest account `rbdpoc2@exampleserver.de` (approved as a throwaway):
   entry active → purge job through all five phases (341 objects
   removed) → entry and registry gone, no ghost registry → repair finds
   nothing → second backfill consistent (32 accounts).
4. imaptest against 0.37.0 re-created the account's data; the account
   re-entered the directory on its own at the first login, which checks
   the creation hook on the cluster. Result: 72 groups, 0 failed, 8
   skipped; base 0/460, extensions 0/272.

The listing metric shows the load the next stage removes: about 51
AdminKV and 79 learning-queue listings in the first 80 seconds after the
rollout.
