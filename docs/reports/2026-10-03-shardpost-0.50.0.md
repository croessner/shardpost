# ShardPost 0.50.0: identifier dictionary filter and text preparation (stage B14h, off)

Date: 2026-10-03

## Change

Second code stage of the plan for the full-text dictionary of large
accounts (`temp/13-fts-dictionary-large-accounts.md`). Everything is off
by default; the defaults keep the behaviour of 0.49.0 exactly.

- **Identifier filter** (`fts.dict_filter: ids`, `fts.dict_id_min_runes`,
  default 25): a body identifier of at least N runes with letters and
  digits gets one start entry in the dictionary instead of its trigram
  keys. Postings stay unchanged; an identifier is found as a whole word
  and by its start, not by a piece from its middle (RFC 9051 §6.4.4
  allows full-word matching for BODY and TEXT; for IMAP4rev1 a
  documented deviation).
- **Text preparation** (`fts.attached_headers: nosig`): signature and
  trace header fields of attached messages are not indexed.
- Both are properties of an index generation (`dx`, `ah`, trust markers
  3 and 4) and need the cluster mark `fts/dictfilter`
  (`shardpostctl fts dictfilter status|enable|disable`); `fts_layout
  -dict-filter` converts the filter exactly, the text preparation needs
  `fts_rebuild`. The scrub repairs marker drift.

Offline measurement (0.49.0 report): with N = 25 and `nosig` the bench
corpus falls from about 292 to about 100 dictionary keys per message.

## Review

Design: two review rounds (plan Fassung 4). Code: one review round by a
second model, which confirmed the default path byte-identical to 0.49.0
and found no false negatives with the filter; fixed: `dictfilter
disable` reads the presence index instead of every account, a sample
instead of repeated full reads, a marker drift case by an older writer,
documentation of the costs of changing N and of `nosig`, and a refusal
of the filter on a layout 2 index.
