# ShardPost 0.34.3: the import inventory of a large shard

Date: 2026-09-30

## Change

An import compares the source with what the target already holds
(`GET .../import/mailboxes/{id}/messages`). The store read a shard with
one omap request for up to 5000 entries and took the answer for complete.
An OSD returns at most `osd_max_omap_entries_per_request` entries (1024)
per request, so of a mailbox with more than 1024 messages in one shard
only the first 1024 were listed. Since imported mailboxes get shards of
100000 UIDs (0.19.0) that is every larger mailbox.

Consequences, all on the importing side — nothing stored was wrong:

- a run sent every message beyond the first 1024 again; the server
  skipped them as existing;
- flag changes and expunges of the source were not applied to those
  messages on a delta run;
- the mailbox was reported as `not verified` ("N source messages
  vanished during the run").

Found when `system@srvint.net` (1348 messages) and `zabbix@srvint.net`
(1301) came back unverified with exactly 1024 messages in the inventory.
The shard is now read in pages until one comes back short. The reading
state of a public folder (`PUT .../readers/{reader}`), which pages
through the same listing, depended on this as well.

`hack/import-live-test.yaml` imported with a shard size of 100, which is
why the live test never met the limit; it now uses 100000 like the
deployment.

- `make lint`: 0 issues; `make test-docker`: green.
- `hack/import-live-test.sh run zabbix@srvint.net` with shards of 100000:
  1301 messages in 22 s, verified; the second run changes nothing and is
  verified; scrub dry run clean.
