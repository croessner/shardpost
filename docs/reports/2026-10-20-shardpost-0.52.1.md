# ShardPost 0.52.1: no empty Content-Type from Email/set

Date: 2026-10-20

## Change

`Email/set` create with a body part whose `type` carried parameters —
an attachment with `"type": "text/calendar; method=REPLY"` — stored a
message with an empty `Content-Type:` field and reported success. The
check of the type allowed the separators of a parameter, and
`mime.FormatMediaType` returns an empty string for a subtype that is not
a token.

- RFC 8621 4.1.4 defines `EmailBodyPart.type` as the media type alone.
  The type of a created part is now parsed strictly; one with parameters
  (or a trailing `;` or blank) is `invalidProperties` on `type`.
  Parameters have their own properties (`charset`, `name`). Blob uploads
  keep accepting a type with parameters.
- The message writer fails instead of writing an empty `Content-Type`;
  the creation then ends in `serverFail` rather than in a broken message.
- `docs/jmap.md` lists the new constraint among those of RFC 8621 4.6.

## Rollout

1. `kubectl diff` showed only the image change; `make deploy` on
   `croessner-nauthilus`, `shardpost-server` and `shardpost-push` rolled
   out (2/2 each, no restarts).
2. No `ERROR` in the server logs after the rollout. From the `mailtest`
   pod (with a PROXY v1 header) IMAP, POP3, LMTP and ManageSieve answer
   with their greetings; the JMAP session resource answers 401 without
   credentials.
