# ShardPost 0.41.0: auth cache and load limits for all protocols

Date: 2026-10-01

## Change

A JMAP client got 503 and 429 answers under load. The 503 came from
authentication: every request and every login went to Nauthilus (and,
for bearer tokens, to the token introspection) with a 10 s timeout, and
there was no cache. The 429 came from a fixed limit of four concurrent
API requests per account, answered at once without a queue. The fix
covers every protocol, not only JMAP.

- **Auth cache** (`auth.cache.*`): successful logins are answered from a
  cache for `ttl` seconds (30, like the Director), refused ones
  optionally for `negative_ttl` (off by default), lookups for
  `lookup_ttl`. Entries are keyed by an HMAC under a per-process key
  over mechanism, user, secret, protocol, TLS state, local address and
  port and, optionally, the client address; no secret is kept in clear.
  Bearer entries end no later than the token's `exp`. Identical requests
  that arrive together share one backend call. `ttl: 0` turns all
  caching off.
- **Flush:** `POST /admin/v1/auth/flush` and `shardpostctl auth flush
  <account>|-all` (role `repair`) empty the entries of an account or all
  of them. The flush reaches every server pod through the flush log
  `auth-flush` in the admin namespace (watch/notify, with a 60 s poll as
  backup); a gap in the log or a lost watch empties everything.
- **Nauthilus client:** `nauthilus.timeout` and
  `nauthilus.http_max_idle_per_host` are configurable; the login attempt
  ordinal per connection and the TLS state (`ssl` empty or `on`) are
  passed as Nauthilus expects them.
- **JMAP limits:** `jmap.max_concurrent_requests` (now 8) with a FIFO
  wait of up to `jmap.limit_wait` (2 s) before a 429, `Retry-After` on
  every 429 and 503, `jmap.max_concurrent_downloads`,
  `jmap.max_event_sources` and an optional per-address limit
  `jmap.max_concurrent_per_ip` (open event sources do not count
  against it).

The Director was fixed alongside: v1.1.3 passes the TLS state to
Nauthilus as `on` or empty instead of `true`/`false`.

## Review

Three review rounds by a second model. Fixed among others: a pod that
failed to read the flush log at start never applied flushes from other
pods, an open event source held its per-address slot for its whole
life, a panic in the shared backend call would have ended the process,
a failing flush log read emptied the cache on every poll, a caller
arriving after a flush could get the answer of a call from before it.

## Rollout

1. 0.41.0 rolled out (server and push); no error in the logs.
2. `hack/auth-smoke.sh` (throwaway account): 7 IMAP logins over 2 pods
   gave 5 hits and 2 misses; `shardpostctl auth flush` on one pod
   reached the other through the flush log (`source="remote"`), the
   next login missed; 16 parallel JMAP requests all answered 200, six of
   them sharing one backend call. The script now runs its logins from
   one exec and skips draining pods: one exec per login took about 5 s,
   so seven of them outlasted the 30 s TTL.
3. imaptest: 72 groups, 0 failed, 8 skipped; base 0/460, extensions
   0/272.
