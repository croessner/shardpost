# ShardPost 0.33.0: push for shared accounts (stage 6c-3) and the stage-5 leftovers

Date: 2026-09-27. Status: rolled out, healthy; JMAP on the test endpoint
`jmap.roessner-net.de`.

## What the release contains

- **Push for shared accounts**:
  - Both the event source and the Web Push worker report changes in shared accounts and in `~public`, keyed by the shared account id.
  - `ShareNotification` changes are reported for the personal account.
  - A new shared account is pushed with all its types. A lost one is pushed once with the state `revoked`, which drives the client to refetch the session.
  - One watch per namespace serves every follower in a process.
  - Watch bounds: `jmap.push.max_shared_watches` (8) per event source and per worker account, `jmap.push.worker_max_watches` (1000) per worker. Beyond them, polling takes over.
  - Principals are not pushed.
- **No activity leak through states**:
  - A shared account's state follows the newest log entry the user can see, not the owner's counter. The per-visibility-set bookmark of that position lives in the owner's namespace under the reserved accessor `~jmap`, where no account can read it. There are at most 256 bookmarks per namespace.
  - `/changes` reads past invisible entries (up to 16 000). `hasMoreChanges` counts only visible ones.
  - Log entries without a mailbox count as invisible.
  - State tokens are sealed with a per-namespace key (a 64-bit keyed permutation), so they can be neither read nor ordered. Shared-account tokens from 0.32.0 no longer parse, and clients resync those accounts once.
  - One case remains: a bookmark restart whose last 1000 log entries are all invisible tells the client that the owner did something.
- **Stage-5 leftovers**:
  - L2: Web Push only to port 443. Other ports are refused at subscription time and never dialled; `allow_internal_endpoints` lifts the rule.
  - L4: the verification queue survives a worker crash (handled items are removed after sending). The cost is a possible duplicate verification with the same code.
  - L5: encoded display names are decoded in every charset Go's text library knows, and a From in such a charset is no longer refused for sending.

## Review

Two Fable rounds.

- **First round**: no rights or data risk. Three should-fix items, all about the owner's hidden activity still being observable, plus a suggested improvement:
  - `/changes` paging returned empty pages with a hidden entry's sequence.
  - Mailbox-less Partial entries counted as visible.
  - First tokens and restarts carried the owner's absolute counter.
  - Keying bookmarks by visibility set rather than by user, suggested to limit the write load on `~public`.
- **Second round**: confirmed all four. It checked:
  - the permutation and the key-creation race (exactly one key per namespace, via compare-and-swap);
  - that the key and bookmarks are unreadable through IMAP METADATA and the admin export/import;
  - that bookmark eviction cannot be driven across tenants.

Known limits, documented:
- A new shared account is noticed at the next poll (30 s event source, 60 s worker).
- API reads write the bookmark (on first use, when it moves, and every 256 entries). The `~public` metadata object is written by its readers, which is untested under heavy load.
- Bookmarks of lost visibility sets stay until evicted.
- Stored envelopes keep their raw encoded names; only new messages benefit from L5.
