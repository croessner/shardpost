# ShardPost 0.38.0: job queue and expiry without listing (scaling stage R1b)

Date: 2026-10-01

## Change

Second stage of the plan to run ShardPost with millions of accounts.
It builds the structures that let the job runner stop listing the
`~admin` namespace, and writes them alongside the existing records
(`admin.kv_index: write`, the default). Reading from them (`read`) is
the switch of the next stage.

- **Due queue** (`model.DueQueue` on the sorted index): keys
  `<due>/<id>/<gen>`, all entries of an id in one shard, a reschedule
  is one RADOS write, `Due(now)` merges the shard heads.
- **Hint indexes** for the admin store collections (`job`, `plan`,
  `idem`, `jmap/push/acct`) in `~admin`, never under `kv.`, so older
  servers ignore them.
- **Job queue** `jobs/claimable`: every change of a job's lease or state
  moves its entry; in `read` mode the runner claims from it and is woken
  by a notify instead of only polling.
- **Expiry** `jobs/expiry` and a single expiry worker under a held
  RADOS lock: jobs, plans and idempotency keys expire with the same
  retention `cleanup()` uses. **Idempotency keys now expire with their
  job** (14 days after it ended); before, they never expired.
  `cleanup()` keeps running beside the worker until `read` is the
  default.
- **Key rotation:** the admin store used by the job runner, JMAP and the
  push worker follows a cephx key rotation (`Store.Rotate`) instead of
  staying on the old connection, which would have stopped working once
  the old key's ticket expired. A pre-existing defect found during this
  stage.
- `shardpost index backfill kv` and `shardpost index show kv`; new
  settings `admin.kv_index`, `admin.kv_queue_shards`,
  `jobs.expiry_seconds`; new metrics `imapceph_queue_ops_total`,
  `imapceph_queue_stale_entries_total`, `imapceph_kv_index_errors_total`,
  `imapceph_job_wakeups_total`.

## Review

Three review rounds by a second model. Found and fixed among others:
the key-rotation defect above (the expiry worker would have kept its
lease on the new connection while working on the dead one), a
use-after-free race between closing a watch and destroying the old
connection's context after a rotation, a librados callback thread that
could block on an unbuffered error channel, and extra listings caused
by wake-ups in `write` mode.

Noted, not changed: go-ceph v0.41 has an internal race between a watch
callback and `Delete` that can panic on a closed channel; it is upstream
behaviour and independent of how ShardPost closes watches.

## Rollout

1. 0.38.0 rolled out; no error in the logs.
2. After the last 0.37.0 pod had drained: `hack/kvqueue-smoke.sh` with
   the throwaway account `rbdpoc2@exampleserver.de`. The backfill read
   88 records (85 indexed and queued); an `index_check` job submitted
   twice with the same idempotency key returned the same job, ran
   through the queue and left exactly the expected entries: no
   claimable entry, job and idempotency key expiring 14 days after it
   ended.
3. imaptest: 72 groups, 0 failed, 8 skipped; base 0/460, extensions
   0/272.

The listings remain in `write` mode by design (about 39 AdminKV and 64
learning-queue listings in the first minutes); switching to `read`
removes the AdminKV ones, and the learning queue follows in the next
stage. The key-rotation path itself has no cluster test; it is covered
by unit tests of the handle bookkeeping.
