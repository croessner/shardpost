# ShardPost 0.53.0: JMAP request metrics, zero instead of nothing

Date: 2026-11-14

## Why

The operator dashboard showed "no data" in most panels. An audit of
all 87 metric families against the source, the pods' `/metrics`, the
cluster Prometheus, the central Prometheus and Grafana found the cause
in the application, not in the collection:

- The scrape and the federation lose nothing: the series names of the
  four pods were the same in the direct output, in the cluster
  Prometheus and in the central one (only scrape meta series are not
  federated).
- 34 to 37 of the 87 families were not exposed by a server pod at all.
  A labelled Prometheus metric has no series before its first event,
  so a counter of failures that had not happened was absent, and
  absent is not zero. Of 140 dashboard queries, 38 returned no series
  and 21 no finite value.
- JMAP had traces and no request metrics.
- `imapceph_rados_notify_seconds` was registered and never observed.
- Three counters did not follow what they describe (below).

The scheduled scrub was not a collection gap: `shardpost scrub
--batch` only writes a batch job; the servers run it and export its
metrics.

## Change

- **JMAP requests** (`internal/jmap/measure.go`): HTTP requests by
  endpoint category and result, their duration and the requests in
  flight; method calls and their duration by method and result — an
  error response inside an HTTP 200 is a result of its call, an unknown
  method name is `unknown`; implicit `Email/set` calls apart from the
  client's; the objects of `/set`, `Email/copy`, `Email/import` and
  `Blob/upload` with the partial failures `not_created`, `not_updated`
  and `not_destroyed`; open event sources and their lifetime; request
  and response body bytes, counted as they pass. A batch is one request
  and as many calls as it has. A client that went away before its
  answer is `canceled`. No account, blob, path or call id is a label.
- **RADOS notify**: `imapceph_rados_notify_seconds{object}` is observed
  around the three notifies of the store (`mailbox`, `account`,
  `queue`).
- **Zero instead of nothing**: `serve`, `push` and `runner` create the
  series of the parts they run when they start
  (`metrics.Init`), and `imapceph_feature_enabled{feature}` names the
  parts the configuration switches off, whose series stay absent.
  [Observability](../observability.md#zero-absent-and-switched-off)
  lists the few series that still appear with their event only.
- **Counters corrected**: a quota recount under the account lock is
  counted (`mode="offline"`; only online runs were); an offline
  `mailbox_delete` that fails while deleting counts as `error`; a
  server that loses worker partition 0 withdraws its count of the
  submission queue instead of exporting its last value.
- 13 new families and `imapceph_feature_enabled`: 101 own families.
  New label `object` on `imapceph_rados_notify_seconds`, which had no
  series before. No existing series was renamed.

## Validation

- `make lint`: 0 issues. `make test-docker` (Ceph test cluster, race
  detector): green. `make man` passes.
- New tests: `TestMetricsBatch`, `TestMetricsSetPartialFailure`,
  `TestMetricsImplicitCall`, `TestMetricsRefusedEarly`,
  `TestMetricsCanceled`, `TestMetricsPanic`, `TestMetricsRedirect`,
  `TestMetricsServerFailure`, `TestMetricsBlobVolume`,
  `TestMetricsEventStream`, `TestMetricsParallel`,
  `TestMetricsCardinality`, `TestHTTPResult`, `TestMethodResult`
  (JMAP); `TestInit` (the series of each role);
  `TestQueueGaugeFollowsTheHolder`; the offline recount in
  `TestQuotaRecalcFTSScrubAndCheck`; and against the Ceph test cluster
  `TestServeExportsItsSeries` (a started server's `/metrics`) and
  `TestNotifyIsMeasured` (each of the three notifies is observed once,
  acknowledged below the timeout).
- One review round (Fable); its findings are fixed in the change: a
  worker without any partition kept its queue count, the feature gauge
  of delayed sending did not follow the worker, the byte counters moved
  only when a request ended, a router redirect counted as an API
  request, `canceled` could override an answer the client had, and
  several test gaps.
- `TestTakeoverKeepsSuccessorLock` failed once under load: it expected
  the lock release in the instant the final state is written. It waits
  for the release now.

   `shardpost-server` (server and import container), `shardpost-push`

   2/2 each, no restarts. No open problem on the three hosts; the
   maintenance was deleted and its absence read back.
4. No `ERROR` in the server or push logs. From the `mailtest` pod (with
   a PROXY v1 header) IMAP, POP3, LMTP and ManageSieve answer with their
   greetings; the JMAP session resource answers 401, the health check
   200, an unknown path 404.

   `docker.io/chrroessner/shardpost:0.53.0@sha256:d61c4becca1acf14d2430cd5faf22f102f166f198be3b46194f485280651c5c7`

## Measured in production

- Each server pod exposes all 85 families expected of a server, each
  push pod all 18 of a push worker; the central Prometheus holds the
  139 series names of the 97 families a running deployment must export
  (5598 series).
- The smoke requests moved exactly their counters: the session request
  without credentials `{endpoint="session",result="unauthenticated"}`
  by 1, the unknown path `{endpoint="other",result="client_error"}` by
  1, the health check nothing; `shardpostctl version` moved
  `shardpost_admin_requests_total{operation="version",code="ok"}` by 1.
- Real client traffic within ten minutes: 165 API requests, 12 session
  requests, 2 event sources (one open, its bytes counted while it
  stays open), seven methods with their calls, p95 of the API requests
  0.92 s, 48 kB in and 592 kB out on the API endpoint, no request in
  flight left behind.
- Dashboard (version 3, built from the catalog): of 125 panels 49 show
  values, 74 a true zero, and two are empty for a stated reason — the
  table of missing families (empty is the target) and
  `imapceph_fts_shard_keys` (set by an offline conversion only).
- 20 alert rules (15 kept, 5 new for JMAP and the collection) are
  healthy and inactive; 34 synthetic scenarios pass with Prometheus
  3.15.1.

## Open

- No delivery and no flag change reached the servers between the
  rollout and this report (Saturday evening), so
  `imapceph_rados_notify_seconds` and the LMTP counters stood at zero
  in production; the notify measurement is proven in the Ceph test
  cluster. The next delivery and the nightly scrub batch (03:17 UTC)
  move them.
- The rendered dashboard was not looked at in a signed-in browser:
  Grafana sits behind the interactive single sign-on and has no image
  renderer. Every query was evaluated through Grafana's datasource
  proxy instead.
- IMAP `UID` commands still share the label `UID`;
  `imapceph_fts_shard_keys` is not set by online runs. Both are
  documented, neither is changed here.
