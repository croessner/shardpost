# ShardPost 0.46.0: layout 3 is the default (stage B14c)

Date: 2026-10-02

## Change

Last required stage of block B14 (plan
`temp/11-fts-write-amplification.md`).

- **`fts.layout` defaults to 3.** It takes effect only with the cluster
  mark (`shardpostctl fts layout3 enable`); without it a server creates
  layout 2 indexes as before. Every server logs the configured layout,
  whether the mark is set and the effective layout at startup and when
  an index creation sees the mark change; the gauges
  `imapceph_fts_layout_configured` and `imapceph_fts_layout_effective`
  show the same.
- **Upgrade note:** a cluster that has the mark set but relied on the
  old default 2 creates layout 3 indexes after this upgrade; set
  `fts.layout: 2` explicitly before upgrading if that is not wanted.
- **`fts_dict_convert` is a legacy kind:** planning it for a layout 3
  account is refused (409, `shardpostctl` exit 65); a run that finds
  layout 3 or a conversion, at its start or later, writes nothing more
  and reports `skipped`.
- Planning `fts_layout -layout 3` without the mark answers 409 instead
  of 503. `shardpost bench measure --convert` follows the effective
  layout. A flaky jobs test was fixed.

## Review

One review round by a second model: a run of `fts_dict_convert` that
found layout 3 in the middle failed instead of reporting `skipped`, a
race could show the wrong mark state in log and gauge until the next
index creation, the bench still demanded `--fts-layout 3`, and the
gauge's value before the mark is read was undocumented.
