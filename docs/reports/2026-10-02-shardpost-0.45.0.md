# ShardPost 0.45.0: full-text layout 3 (stage B14b)

Date: 2026-10-02

## Change

Second stage of block B14 (full-text write amplification, plan
`temp/11-fts-write-amplification.md`, final after five design review
rounds). Layout 3 is off by default; a server creates it only with
`fts.layout: 3` and the cluster mark.

- **Layout 3:** each account has its own full-text objects of one
  generation, `ftx/<gen>/p<i>` (postings, by compare-and-swap),
  `ftx/<gen>/d<j>` (trigram dictionary) and `ftx/<gen>/h<k>` (head
  texts), their numbers recorded in the layout record `L` of `ftsmap`.
  A new account starts with one object of each kind; the `fts_due`
  worker reshards an account whose objects outgrow
  `fts.shard_target_keys`.
- **Writers never create index objects;** an anomaly (frozen object,
  missing object, other generation) makes them read `L` and retry in
  the current generation, within a fixed budget, or answer 451.
- **`fts_layout` job** (repair, exclusive): conversion 2 → 3, reshard
  and the way back 3 → 2, with tokens that carry the job's lease
  generation, a freeze of the sources, fencing before every switch, and
  clean-up by the job, the runner, every lock taker and the scrub.
- **Import reshard endpoint**
  (`/admin/v1/accounts/{account}/import/fts-reshard`): `migrate`
  reshards between batches under its own import lock.
- **Server registration** (`servers/<instance>` in the admin store) and
  the cluster mark: `shardpostctl fts layout3 status|enable -pods
  N|disable|list`, `shardpostctl fts layout show|clear`.
- Purge, sweep and scrub know every generation; IMAP answers `NO
  [UNAVAILABLE]` while an index is not available.

## Review

Three review rounds by a second model for the code (after five for the
design). Fixed among others: dictionary keys lost when an indexing was
retried within one generation (it also affected layout 2), empty
accounts converted without the trusted-index marker, a search session
that cached layout 2 across a conversion and then found nothing, a
leftover old generation after a crash between switch and clean-up, a
mutex held over store reads in the reshard endpoint, and clean-up of a
running import reshard by a manual `clear`.

## Rollout

1. 0.45.0 rolled out (server and push); no error or warning in the
   logs. Both servers registered (`fts layout3 status`: 0.45.0, fresh,
   capability `fts_layout3`); the mark is not set.
2. imaptest: 72 groups, 0 failed, 8 skipped; base 0/460, extensions
   0/272. `hack/auth-smoke.sh`, `hack/r3-smoke.sh` and
   `hack/r5-smoke.sh` passed.
3. Bench on the R4 bench pools, 20 probe accounts (`shardpost bench
   measure --fts-layout 3 --convert`, then delivery, contention, expunge
   and search in layout 3):

| Measurement | 0.44.0 (layout 2) | 0.45.0 (layout 3) |
|---|---|---|
| Operations per delivery | 226.4 | 24.2 (13.1 reads, 11.1 writes) |
| Delivery latency, one at a time | p50 295 ms, p99 590 ms | p50 88 ms, p99 198 ms |
| Four at a time into one account | 7.3/s, p50 524 ms, 0.56 CAS retries | 17.9/s, p50 191 ms, 0.82 CAS retries |
| EXPUNGE of one message | 204 operations, p50 301 ms | 28.2 operations, p50 128 ms |
| Search query | 39.7 reads, p50 35 ms, p99 80 ms | 9.4 reads, p50 15–18 ms, p99 38–60 ms |
| Search result fingerprint | `08381cf9…` | `08381cf9…` (identical) |
| Conversion 2 → 3, account lock | – | p50 3.4 s, max 4.2 s |
| Reshard of a converted account | – | 141 operations |

The full-text index falls from 225 of 245.6 operations per delivery
(R4) to about 7. With four deliveries at a time into one account the
retries rise (one postings object instead of sixteen), the throughput
still more than doubles.
