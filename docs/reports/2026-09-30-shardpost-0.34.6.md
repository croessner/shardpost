# ShardPost 0.34.6: review of the import hotfixes

Date: 2026-09-30

0.34.1 to 0.34.5 were written during a live migration and rolled out
without a second reader. A review by a second model afterwards found the
following; all of it is fixed here.

| Finding | Resolution |
| --- | --- |
| Since 0.34.2 a batch writes its blobs first and indexes them afterwards. A run killed in between left blobs that the next run found, shared and did not index: "the blob exists" was taken for "the message is indexed". The kills of the server during the import of `de10000@srvint.net` fell into that window, so up to 200 messages per kill may be missing from its full-text index | Every blob of a batch is indexed, shared or not; indexing a message twice changes nothing. The index of the account is rebuilt (`fts_rebuild`) |
| The inventory of a shard (0.34.3) ended at a short page. That is the end only if the OSD's per-request limits equal the page size asked for; with a smaller entry or byte limit it would stop after the first page again | It ends at an empty page, and at a page that does not get past its start |
| The posting lists of a batch were read by keys in one request of any size, and a key the read does not return is written afresh | The terms go through in pieces of `omapPageSize`, like the other reads by keys in the store |
| `fts_rebuild` indexed message by message | It indexes in batches of 200 messages or 8 MiB |
| An account import dropped the root mailbox of another namespace (0.34.1) without a word | The report names it in a warning |
| A comment gave "over 1 GiB" where "over 800 MiB, killed at the limit of 1 GiB" was measured | Corrected |

Verified by the review and left as it is: batched and per-message
indexing produce the same posting lists and dictionary; duplicate GUIDs
in a batch; a failure halfway through the indexing of a batch is undone
consistently; the bounded dictionary update is correct under concurrent
writers.

Not changed, outside these fixes: `ListMailboxesAfter` and `ListSharedN`
hand a caller's limit to one omap read and would meet the same limit for
an account with more than 1024 mailboxes or shares in one page.
