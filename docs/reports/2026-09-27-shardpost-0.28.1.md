# ShardPost 0.28.1: shard gate, certificate reload, JMAP provisioning

Date: 2026-09-27. Status: rolled out, healthy. JMAP stays off (`jmap.addr`
is not set); this release prepares the public JMAP endpoint.

## What the release contains

- **Shard gate** (`jmap.shard_attribute`, `jmap.shard`). JMAP serves only
  the accounts the authentication backend assigns to this shard (Nauthilus
  with the Director returns `mailShard`). Any other account, and one
  without the attribute, is answered 403 before its store is opened. A
  load balancer in front of one shard lets every account of the deployment
  reach the server; without the gate an account whose mail lives elsewhere
  would see an empty account and write into this shard. JMAP without a gate
  warns at startup; a result without the attribute is logged once as a
  likely misspelt attribute name.
- **Certificate reload** (`internal/certfile`, `tls.reload_seconds`,
  default 60). The IMAP/POP3/Sieve certificate and the JMAP certificate
  are reloaded when the content of their files changes, so a certificate
  cert-manager renews in a mounted Secret reaches the listeners without a
  restart. Handshakes read the certificate lock-free; a renewed pair that
  does not load is logged and the old one kept.
- **JMAP provisioning.** Fetching the session resource gives an account its
  INBOX and the `server.autocreate` mailboxes and refreshes its quota, as
  an IMAP login does. The mailbox provisioning moved from `imapproto` to
  `provision.Mailboxes`; IMAP behaviour is unchanged.

## Review

Two Fable rounds. The first (on `97e988f`) found no code defect but
corrected the documentation (a foreign-shard account does not get
mailboxes created, it sees an empty account and writes into the wrong
shard), asked for case-insensitive attribute names, a startup warning, a
handshake path without a mutex and renewal detection by content, more
tests, and noticed that JMAP did not provision accounts. Its deployment
findings belong to the activation: the shard gate in the same change as
`jmap.addr`; the network policy admitting the JMAP port only from the
HAProxy addresses; `externalTrafficPolicy: Local` and those addresses in
`server.proxy_protocol_trusted_cidrs`, verified with a deliberate failed
login. The second round (on `8098db0`) confirmed the IMAP login path
unchanged and found three small points, fixed in `0101224`.
