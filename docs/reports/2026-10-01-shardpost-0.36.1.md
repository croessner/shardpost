# ShardPost 0.36.0 and 0.36.1: closing the gaps of the protocol reference

Date: 2026-10-01

## Why

[Protocols, features and RFCs](../protocols.md) listed, after the audit
for 0.35.2, what the server did not implement or implemented only in
part. This release implements those points instead of documenting them
away. Every change was built on its own branch, reviewed by a second
model in two to four rounds until no finding was left, merged, and then
checked together with `make lint`, `make test-docker` and a complete
imaptest run.

## Findings and their state

| # | Finding (0.35.2) | Now (0.36.1) |
|---|---|---|
| 1 | Full-text search indexed body text without charset conversion (ISO-8859-1/Windows-1252 umlauts not found), HTML as markup | All text converted to UTF-8 (WHATWG charsets, `fts.fallback_charset`), HTML reduced to visible text (`fts.html`), file names and attached messages indexed; preview from one alternative |
| 1a | imaptest `search-body`, `search-header`: IMAP SEARCH matched words, not substrings | RFC 3501/9051 substring semantics by default (`fts.imap_search`), the index as a candidate filter for every key in the tree, a stored decoded header per message, parallel verification (`fts.verify_parallel`), index version marker |
| 2 | LMTP added neither `Return-Path` nor `Delivered-To` | Both, before `Received`, also for local delivery; `server.lmtp_return_path`, `server.lmtp_delivered_to` |
| 3 | `UTF8=ACCEPT` advertised without effect, no modified UTF-7 | Modified UTF-7 for sessions without UTF-8, UTF-8 for sessions with `UTF8=ACCEPT` or `IMAP4rev2`; `APPEND … UTF8`, NFC names with `OLDNAME`; IMAP4rev2 session behaviour after `ENABLE IMAP4rev2`; job `mailbox_name_convert` for names older clients stored in modified UTF-7 |
| 4 | Advertised but incomplete: `SAVEDATE` search keys, `QUOTASET`, `[MAILBOXID]` on `CREATE` | All present; also `STATUS DELETED-STORAGE`, `PREVIEW (LAZY)`, `[BADURL <url>]`, `SORT=DISPLAY`, `[UNKNOWN-CTE]`, ENVELOPE source routes, SORT/THREAD charset and unknown keys |
| 5 | JMAP: no `SearchSnippet/get`, no `hasAttachment` filter, mailbox tree options ignored | All three; `hasAttachment` stored at delivery, older messages filled by job `attachment_backfill` or in the background |
| 6 | `server.insecure_auth` defaulted to true | Defaults to false |
| 7 | Last imaptest run was 0.11.0 | 0.36.1: 72 groups, 0 failed (see below) |
| 8 | JMAP and ManageSieve not traced | Spans for both; personal attributes (accounts, mailboxes, client addresses, error texts) only with `telemetry.user_attributes` (default off) |
| 8 | Sieve `:days 0` meant 7 days | `sieve_vacation_min/max/default_period` (Pigeonhole semantics; `0` with minimum 0 answers every message) |
| 8 | `reject` was a plain LMTP 550 | RFC 8098 MDN to the sender, protocol rejection for automatic and list mail or with `sieve_reject_mode=protocol`; `ereject` keeps 550 |
| 8 | No Sieve `fcc` | `:fcc` with `:create`, `:flags`, `:specialuse` for `vacation` and `notify` (RFC 8580) |
| 8 | No ManageSieve `UNAUTHENTICATE` | Command and capability (RFC 5804 §2.14.1) |

Found and fixed on the way: `$` in `UID EXPUNGE` and the `UID` search key,
LMTP `MAIL`/`RCPT` before `AUTH` now `530 5.7.0`, NOTIFY answers every
unsupported event with `NO [BADEVENT]`, an explicit `keep` stays across
the before/personal/after script sequence.

Not part of this release: contacts and calendars (CardDAV/CalDAV, JMAP),
JMAP WebSocket and MDN, RFC 6857/6858 downgrade, `ESORT`/`CONTEXT`.
The remaining documented deviations are listed in
[Protocols, features and RFCs](../protocols.md).

## Rollout

1. 0.36.0 rolled out (`shardpost-server`, `shardpost-push`); the
   capabilities were checked from the mailtest pod (`fcc`,
   `UNAUTHENTICATE`, `NOTIFY "mailto"` in ManageSieve).
2. `fts_rebuild` for every account, one after the other:

   | Account | Messages | Time |
   |---|---|---|
   | de10042@srvint.net | 954 | 30 s |
   | de10000@srvint.net | 36158 | 710 s |
   | lists@srvint.net | 75 | 16 s |
   | system@srvint.net | 1372 | 30 s |
   | zabbix@srvint.net | 1301 | 32 s |
   | de10043@srvint.net | 718 | 27 s |
   | spamtrap@srvint.net | 351 | 29 s |
   | ~public | 29844 | 511 s |
   | rbdpoc2@exampleserver.de | 26 | 17 s |

3. imaptest against 0.36.0 failed only `atoms`: a `LIST` pattern that
   is not modified UTF-7 was refused. 0.36.1 takes such a pattern as it
   stands; imaptest against 0.36.1: **72 groups, 0 failed**, 0 of 460
   base and 0 of 267 extension commands, 9 groups skipped for
   capabilities not offered.
4. `attachment_backfill` for the same accounts (70 797 messages in
   total, none unreadable), so a JMAP `hasAttachment` query never has
   to fill on demand.
5. `mailbox_name_convert` was not needed: no stored mailbox name of a
   live account is in modified UTF-7 (checked before the release).

Clients that enable neither `UTF8=ACCEPT` nor `IMAP4rev2` now see
non-ASCII folder names in modified UTF-7 (`Entw&APw-rfe` for
`Entwürfe`), as RFC 3501 requires; such a client may resynchronise
these folders once.
