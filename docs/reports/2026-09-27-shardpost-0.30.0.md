# ShardPost 0.30.0: JMAP Blob and SieveScript (stage 6b)

Date: 2026-09-27. Status: rolled out, healthy; JMAP on the test endpoint
`jmap.roessner-net.de`.

## What the release contains

- **Blob management (RFC 9404, `urn:ietf:params:jmap:blob`)**:
  - `Blob/upload` builds blobs from text, base64 and ranges of other blobs, including `#creation` references and in any order. A cycle ends in `blobNotFound`.
  - `Blob/get` returns data as text, base64 or both, with `isEncodingProblem`/`isTruncated`, and `sha`/`sha-256` digests.
  - `Blob/lookup` covers Email, Mailbox, Thread and SieveScript.
  - Limits:
    - A Blob/upload call takes a slot of the per-account upload counter.
    - All creations of one call build at most `jmap.max_size_blob_set` bytes.
    - `jmap.max_data_sources` bounds the sources per creation.
    - One Blob/get returns at most `jmap.max_size_blob_get` of data and digested bytes.
    - The per-call cache of read messages and parts is bounded in bytes.
- **Sieve scripts (RFC 9661, `urn:ietf:params:jmap:sieve`)**:
  - `SieveScript/get`, `/set` (with `onSuccessActivateScript`/`onSuccessDeactivateScript`), `/query`, `/validate`. `/queryChanges` answers `cannotCalculateChanges`. The RFC defines no `/changes`.
  - Scripts are compiled like ManageSieve PUTSCRIPT; errors are `invalidSieve`.
  - An update renames first and writes the content second, and renames back when the write fails.
  - Script contents are blobs (`S` + SHA-256 prefix).
  - Ids are derived from the name (`n` + hash). Only ids that differ, from JMAP creation or a JMAP rename, are kept in a server-managed metadata record, and listing writes nothing.
  - The `jmap-vacation` display copy is read-only.
- **Script names up to 512 bytes** (RFC 9661) across ManageSieve, the Ceph store, the admin API, the archive and JMAP.
- **ManageSieve `MAXREDIRECTS` reports 4**, which is what delivery always allowed.
- **Ceph `RenameScript`** writes the omap rename and the active-name xattr in one version-checked operation. The active name can no longer point at a missing script, which would have made delivery run unfiltered for a moment.

## Review

Three Fable rounds.

- **First round.** No blocker, but three findings before release:
  - Blob/upload could write a lot per call outside the upload throttling.
  - Source parts were read in full again and again, and digests were not budgeted.
  - A failed rename left the new content written.
  
  It also recommended script names up to 512 bytes, degradation when the id record overflows, and `created.type: null`.
- **Second round** (on the fixes). The new per-call cache held every message for the whole call with no bound. It is now bounded in bytes. The round also brought in the derived-id design and the atomic Ceph rename.
- **Third round.** No blocker. Two small points were fixed in `bc38d5d`:
  - a source vanishing between check and read is `blobNotFound`;
  - id placeholders are kept only for derived ids, so the record does not grow with every rename and destroy.

Known limits, documented:
- Script writes are not pushed.
- A script renamed over ManageSieve gets the derived id of its new name.
- A script that only compiles for IMAP events stays inactive after `onSuccessActivateScript`.
- The single-op Ceph rename is tested in its pure part only; it was also exercised live, below.

## Live acceptance (public test endpoint, test accounts)

- `hack/jmap-acceptance-stage6b.py`:
  - **Capabilities:** `blob` and `sieve` are present. The account capabilities say:
    - Sieve: `maxSizeScriptName` 512, `maxSizeScript` 262144, `maxNumberRedirects` 4, 38 extensions.
    - Blob: Email, Mailbox, SieveScript and Thread, with `sha-256`/`sha`.
  - **Blob:** Blob/upload from text and base64 sources and a range of the first blob gives the expected sizes. Blob/get round-trips the content and the range, and the SHA-256 matches. Blob/lookup finds a real message and its INBOX.
  - **SieveScript:**
    - A script is created and stays inactive.
    - An invalid one is `invalidSieve`, and `/validate` agrees.
    - A rename keeps the id.
    - Creating `jmap-vacation` is `forbidden`.
    - Destroy works, and the account's active script is unchanged.
- **Regression:** `hack/jmap-acceptance.py` and `hack/jmap-acceptance-stage6a.py` both passed. Sending and refusals work, Quota is unchanged, and the vacation reply arrived once.

## HAProxy during rollouts

The first 6b run right after the rollout timed out on the session fetch. With `externalTrafficPolicy: Local` a node that has just lost its pod stopped answering, and HAProxy took up to a minute (`inter 30s`, `fall 2`) to mark it down.

The backend `be_shardpost_jmap` now fails over like the Nauthilus backend:
- `inter 5s`
- `timeout connect 3s`
- `option redispatch`
- `retries 2`
- `retry-on conn-failure empty-response`

The change was made with rns-server `services/haproxy/jmap-failover.py`: backup, `haproxy -c`, soft reload, Zabbix maintenance 394.

Verified by a `rollout restart` during which a pod moved from kn2 to kn1: 128 authenticated session requests at one per second, none failed, none took 5 s or longer.
