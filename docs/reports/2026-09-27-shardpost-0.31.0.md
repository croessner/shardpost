# ShardPost 0.31.0: JMAP sharing (stage 6c-1)

Date: 2026-09-27. Status: rolled out, healthy; JMAP on the test endpoint
`jmap.roessner-net.de`.

## What the release contains

- **Shared accounts (RFC 8621 sharing model)**:
  - Mailboxes other owners share with the user, and the public folders `~public`, appear in the session as extra accounts.
  - These accounts have `isPersonal: false` and offer only `urn:ietf:params:jmap:mail`.
  - `isReadOnly` is true unless the user holds one of `i w s t e x` somewhere in the account.
  - Owners are found through the user's shared pointers, as IMAP LIST finds them. A mailbox shared only with `anyone` is not listed, as in IMAP.
- **Rights as in IMAP (RFC 4314)**:
  - A shared account shows only mailboxes with `l`. Messages are only found in mailboxes with `r`, including full-text hits and thread members.
  - `myRights` maps the ACL: read from `l`+`r`, add from `i`, remove from `t`+`e`, `$seen` from `s`, other keywords from `w`, rename/delete from `x`. `maySubmit` is always false.
  - Every write checks its rights before the first store call. A missing right is `forbidden`, and nothing is written or dropped silently.
  - No mailbox creation in shared accounts: the store does not inherit the parent's ACL, so the creator could not see the result.
  - Destroying a mailbox without `r` needs `onDestroyRemoveEmails`, so emptiness is not revealed.
  - Unknown, foreign and unshared account ids answer `accountNotFound`. Methods outside Mailbox, Email and Thread answer `accountNotFound` for a shared account.
- **Public folders**: `\Seen` is private per reader, stored and versioned as in IMAP.
- **`Email/copy` between accounts**, personal and shared in either direction. The copy gets a new id. `onSuccessDestroyOriginal` needs `t`+`e` on the source.
- **Blobs**: in a shared account a blob is only a readable message or a part of one. That applies to download, import, parse and body-part references. Uploads into a shared account are refused.
- **Bounded cost**:
  - The state in every API response hashes a bounded read of the user's pointers and opens no owner namespace.
  - `jmap.max_shared_accounts` (64) caps the owners in the session.
  - `jmap.max_shared_mailboxes` (1000) caps the pointers per owner.
  - `jmap.max_session_pointers` (8 × the latter) caps the pointers for the whole session. An owner that does not fit is skipped, not the rest of the list.
  - Rights are read once per method call.
- **Revocation tombstones** in the pointer registry expire after one hour, do not count against listing limits, and are collected during listings.
- **ACL identifiers** with `/`, NUL or invalid UTF-8 are refused: IMAP SETACL/DELETEACL answer `BAD`, the admin API 400.

Not yet: Principals, `shareWith` and ShareNotification (6c-2), and push for shared accounts (6c-3).

## Review

Four Fable rounds. None found an authorization bypass.

- **First round**:
  - Mailbox/query in a shared account echoed the personal account id.
  - Each API response opened every sharing owner and looked up every pointer. One owner sharing thousands of mailboxes made every request of the grantee expensive.
  - Rights were reloaded per item.
  - Destroy without `r` revealed whether a mailbox was empty.
  - Nits on `isReadOnly`, the docs and tests.
- **Second round**:
  - One hostile owner sorting first could use up the session's pointer budget and hide every later owner.
  - The fingerprint read was unbounded.
- **Third round**: revocation tombstones were never collected. An owner could share and revoke 8000 mailboxes and fill the bounded window for good, so later grants no longer moved the session state.
- **Fourth round**: confirmed these fixes. Two follow-up nits:
  - Existing ACL entries with `/` in the identifier, if any exist, can no longer be removed through IMAP or the admin API.
  - With more than 16,000 fresh tombstones, every API response reads the full key budget for up to an hour.

Known limits, documented:
- A change of `anyone` entries, or a grant beyond the first `max_session_pointers` pointers, reaches a client only when it next fetches the session resource.
- A private `\Seen` change in a public folder is reported to every reader's `Email/changes` as an update.
- JMAP does not remove private `\Seen` marks of expunged messages; IMAP SELECT does.
- No `Quota/*` for `~public`.
- A rename onto a hidden mailbox's name says the name is taken, as IMAP does.

## Live acceptance (public test endpoint, test accounts)

- `hack/jmap-acceptance-stage6c.py`: `rbdpoc1` owns a fresh mailbox with one message and shares it with `rbdpoc2` over IMAP SETACL.
  - Before the grant, no shared account is listed.
  - With `lr` the account appears with `isPersonal` false, `isReadOnly` true, and capabilities `core` and `mail`.
  - Exactly the one mailbox is visible, with `myRights` read true, add/keywords/delete/submit false, and one email.
  - `Email/query` and `Email/get` return the message.
  - A keyword without `w` is `forbidden`. `Email/copy` into `rbdpoc2`'s INBOX works.
  - With `lrsw` the keyword is set, and destroy without `t`/`e` is still `forbidden`.
  - After DELETEACL the account is gone from the session, and `Mailbox/get` answers `accountNotFound`.
  - Cleanup removed the mailbox and the copy.
- IMAP `SETACL INBOX bob/x lr` answers `BAD Invalid identifier`.
- **Regression:** `hack/jmap-acceptance.py`, `-stage6a.py` and `-stage6b.py` passed.
  - Sending and delivery worked in about 5 s, with `forbiddenFrom`/`forbiddenMailFrom` refused.
  - Quota and the vacation reply (exactly one, in about 10 s) worked.
  - Blob and SieveScript worked.
