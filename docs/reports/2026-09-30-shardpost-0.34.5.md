# ShardPost 0.34.4 and 0.34.5: memory of an import into a large account

Date: 2026-09-30

## What happened

The import of `de10000@srvint.net` (36050 messages, 1.7 GB) killed the
server container of the pod it ran against four times (`OOMKilled`,
limit 1 GiB): once with 0.34.1 after an hour of importing, and three
times with 0.34.2 to 0.34.4 within seconds of the first batch into
INBOX, when the account already held some 20000 messages. Each time the
other pod kept serving; sessions on the restarted pod were dropped and
the import run ended.

## Cause

Sampling `process_resident_memory_bytes` and the Go heap once a second
showed the resident size going from 60 MiB to over 800 MiB while the Go
heap held 240 MiB: the memory was in librados, outside `GOMEMLIMIT`.

The objects of the account's full-text index were then measured in the
pool:

| Object | Entries | Bytes of values |
| --- | --- | --- |
| `fts/00` (posting lists, one of 16 shards) | 83507 | 1.3 MiB |
| `ftsd/00` (trigram dictionary, one of 16 shards) | 3092 | 21 MiB |

The trigram dictionary of this account is about 340 MiB. An entry lists
up to 2000 terms and is read and written whole. The new terms of one
message touch a few hundred entries; the new terms of a batch touch most
of them, and the dictionary update took all sixteen shards at once. With
the per-message indexing before 0.34.2 the same data went through memory
message by message, which is what made that import slow (250 ms per
message) and its memory grow.

0.34.4 took the posting lists for the cause and sent them through one
shard at a time; it still killed the container. 0.34.5 corrects that:
the dictionary update of a batch takes one shard after the other in
pieces of 256 trigrams, and postings are parallel again.

## Allocator arenas

With 0.34.5 the import ran, but the resident size still grew by about
17 MiB a minute (414 MiB to 551 MiB in eight minutes) with a Go heap of
40 MiB: glibc keeps one arena per thread, and the client library's
threads fragment them with allocations of this size. The overlay now
sets `MALLOC_ARENA_MAX=2` for the server container. With it the resident
size stayed between 250 MiB and 310 MiB over the rest of the import
(peaks up to 460 MiB).

## Open

- The trigram dictionary costs 340 MiB for an account of this size and
  is rewritten, entry by entry, whenever new terms arrive. That bounds
  how fast an import into a large account can be (about five messages a
  second here) and is what a delivery of a message with many new terms
  pays as well. It needs a different layout; nothing in this release
  changes it.
- An import into an empty account runs at 20 to 60 messages a second.

## Validation

- `make lint`: 0 issues; `make test-docker`: green.
- The import of `de10000@srvint.net` resumed on 0.34.5 and ran through
  the remaining 5900 INBOX messages and the following mailboxes without
  a restart of the server.
- Image `docker.io/chrroessner/shardpost:0.34.5@sha256:1adbc15f95e766df29da266e8bd1a9ccae10104a996df67251dccd905ab4c6ac`.
