# ShardPost 0.51.0: online reshard and rebuild of the full-text index (stage B14i)

Date: 2026-10-03

## Change

Reshards, layout and filter conversions (`fts_layout`) and rebuilds
(`fts_rebuild`) of the full-text index can run online: without the
account lock, so deliveries, logins and running sessions carry on (plan
`temp/14-fts-online-reshard.md`, Fassung 3 after two design review
rounds).

- **Capture via the id map:** while a run is active, every indexing
  records its message in the id map's compare-and-swap (`w:<guid>`,
  counter `w#`); writers keep writing to the current generation.
- **The run** builds the new generation alone (copy from the postings,
  or re-reading the messages for a rebuild), catches up the captured
  messages and switches with one compare-and-swap; if it cannot catch
  up it holds new deliveries for at most `fts.build_hold_ms` (2 s),
  never with 451.
- **Barriers:** a soft freeze bound to the run; writers of older
  versions see a hard freeze; the run writes only to its target.
- **Cluster mark** `fts/online` (`shardpostctl fts online
  status|enable|disable`); without it everything runs as in 0.50.0.
- **Night window** `fts.reshard_window` with time zone for the `fts_due`
  worker and batch runs; a run starts only if its estimate fits; an
  account above `fts.reshard_urgent_factor` (1.8) of its target is
  resharded at once, online.
- `fts.online_build: auto` makes online the default for runs when the
  mark is set.

## Review

Two design review rounds and one code review round by a second model:
a writer that could have written through a hard freeze of a later
offline run, the capture of a message re-indexed during a run, orphan
ids blocking a rebuild, a runner fallback for online runs, urgent
accounts postponed inside the window, a skipped unreadable message
under a trusted index marker, and three missing tests; all fixed.

## Rollout

1. 0.51.0 rolled out (server and push); no error in the logs (one
   transient warning of the OIDC introspection). imaptest: 72 groups, 0
   failed, 8 skipped; base 0/460, extensions 0/272. Auth, kvqueue,
   learning, R3 and R5 smoke tests passed.
2. `shardpostctl fts online enable -pods 2`.
3. The throwaway account `rbdpoc2@exampleserver.de` filled with 1 822
   bench messages (`shardpost-load -corpus ids`). While it filled, the
   `fts_due` worker resharded it twice offline (1/1/1 → 1/4/1 → 2/8/1,
   12–15 s each): 178 deliveries were deferred with "account locked" —
   the overlay did not yet set `fts.online_build`. Exactly the effect
   this stage removes.
4. Overlay: `fts.online_build: auto`, `fts.reshard_window:
   "02:00-05:00"`, `fts.reshard_window_tz: Europe/Berlin`.
5. `hack/online-smoke.sh` (rbdpoc2): online `fts_rebuild` of 1 832
   messages in about 50 s while 5 messages were delivered (all accepted
   and caught up), an IMAP session sent 13 NOOPs, a POP3 login and a
   JMAP session request succeeded; no lock refusal in the logs. The
   script's LMTP address (the server pod's own listener), its output
   parsing and its JMAP session path were fixed on the way.
