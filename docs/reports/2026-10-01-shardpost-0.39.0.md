# ShardPost 0.39.0: no pool listing in running paths (scaling stage R2a)

Date: 2026-10-01

## Change

Third stage of the plan to run ShardPost with millions of accounts.
After this release no running path lists RADOS objects any more; only
the nightly scrub still does (next stages).

- **`admin.kv_index: read` by default:** the job runner claims from
  `jobs/claimable`, is woken by notify, `cleanup()` is gone (the expiry
  worker does it), the push worker scan and job lists read the hint
  indexes. A gate keeps a server in `write` behaviour (with a warning)
  until the kv backfill marker exists.
- **Learning queue without listing:** a due queue and an owner index in
  the index-pool namespace `~learning`; the message copy stays in the
  data pool. The worker holds its lease (same lock as before, so old and
  new workers never run at once) and is woken by notify. Purge and the
  admin list use the owner index. `imapsieve.learning.index`
  (`write` by default; `read` after `shardpost index backfill
  learning`).
- **Log trimming without full reads:** the mailbox and account change
  logs are trimmed from their header counters, reading only the keys to
  remove.
- **Per-account limits** against large omap objects (`limits.*`):
  mailboxes 10000, used names 50000, keywords per mailbox 1000,
  metadata entries 1000, shared pointers 10000. IMAP `NO [LIMIT]` /
  `NO [METADATA TOOMANY]`, JMAP `overQuota` / `tooManyKeywords`, admin
  `409 limit_exceeded`. Mail is never refused for a limit: a Sieve
  `fileinto` that would create a mailbox over the limit goes to INBOX,
  keywords over the limit are dropped.

## Review

Two review rounds by a second model. It confirmed that the new log
trimming cannot remove change records a client could still reach
(imported history is below the log start already), that old and new
learning workers exclude each other, and that the read-mode gate is
safe in a mixed fleet. Fixed among others: the JMAP error type for the
keyword limit (`tooManyKeywords`, RFC 8621), orphaned dead learning
entries, a double mailbox check per Sieve delivery, and one store view
per worker pass instead of one per job.

## Rollout

1. 0.39.0 rolled out (kv index already backfilled with 0.38.0, so
   `read` took effect at once); no error in the logs.
2. `hack/learning-smoke.sh` with the throwaway account
   `rbdpoc2@exampleserver.de`: learning backfill (0 jobs, completion
   marker set).
3. Overlay switched to `imapsieve.learning.index: read` and rolled out.
4. Check after the switch: on both server pods the listing counter
   `imapceph_rados_listings_total` does not appear at all (no listing
   since start); the learning worker answered 147 due reads, the job
   runner 30, with no listing.
5. imaptest: 72 groups, 0 failed, 8 skipped; base 0/460, extensions
   0/272.
