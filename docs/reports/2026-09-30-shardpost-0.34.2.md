# ShardPost 0.34.2: an import batch is indexed in one pass

Date: 2026-09-30

## Change

The account import stored the blobs of a batch and then indexed every
message on its own for the full-text search: the document id map, one
read and one compare-and-swap per posting shard (16), the dictionary.
That is some forty round trips per message, against posting lists that
grow with the account. The first large live import
(`de10000@srvint.net`, 36050 messages, 1.7 GB) ran at about four messages
a second; a batch of 200 messages took 49 seconds in the server while
the importer sat idle.

The new blobs of a batch are now indexed together
(`ftsIndexDocs`): the id map, each posting shard and the dictionary are
written once per batch. Delivery and APPEND index one message as before,
through the same function.

## What was observed and is not changed here

- **Memory.** The server container (limit 1 GiB) was killed by the
  kernel during the import. 0.34.5 has the cause and the fix; see
  [its report](2026-09-30-shardpost-0.34.5.md).
- **Concurrent imports** share the memory budget
  (`server.memory_budget_bytes`); several large batches at once exhaust
  it and the API answers `503 temporary` after ten seconds. Run account
  imports one after the other.
- **Pruning a large mailbox** took about ten minutes for 5000 messages.

  do not talk to a cluster).
- `hack/import-live-test.sh run zabbix@srvint.net` with the new image
  against the live pools, namespace `importtest`: 1301 messages in 56 s
  (23 messages a second), second run changes nothing, all mailboxes
  verified; `SEARCH TEXT zabbix` finds 1301, `SEARCH SUBJECT problem`
  574, a word that does not occur 0; scrub dry run reports no orphan or
  missing blob.
