# 0.27.0: an account-wide state, and JMAP Core on top of it

Released 2026-09-21. Roadmap [stage 6](../../ROADMAP.md#stage-6-jmap-in-full--in-progress),
built in stages; what the release contains and what it does not is in
[JMAP](../jmap.md).

## What changed

**The account change log** (stage 0 of the staged plan). IMAP counts
MODSEQ per mailbox, JMAP wants one number per account. A new object
`account` per account holds that counter and the entries behind it; see
[RADOS storage](../architecture/storage.md#the-account-change-log) for
the layout and the two-phase write it needs, because a mailbox and the
account object cannot be written atomically together.

Every write path of both stores is bracketed by it, including the
scrubber's repairs and the account import. That is the cost of the
release for accounts that will never see a JMAP client: two small omap
operations per write.

**JMAP Core** (RFC 8620, stage 1) in `internal/jmap`: session resource,
API endpoint with batching and back-references, error model, limits,
Basic and Bearer through the existing Nauthilus backend, blob upload and
download with byte ranges. It is **off in this release**: the overlay
sets no `jmap.addr`, and without one the front-end is not started. The
startup line of the running pods shows `"jmap":""`.

## The user path

An IMAP session against the live service (`shardpost:993`, test account
from `imaptest-creds`) ran CREATE, APPEND, SELECT, UID STORE, EXPUNGE,
CLOSE and DELETE. Every command answered OK; the scratch mailbox was
removed again.

The account log of that account afterwards, read with `rados
listomapvals account`, held exactly six entries in the order of the
session — mailbox created, email created (UID 1 with its GUID), email
updated, email destroyed, the partial message entry of the DELETE, and
mailbox destroyed — with `h:seq` at 6 and no announcement left
uncommitted. That is the check the staged plan asked for: an IMAP
session does its work, and the account log holds exactly those changes.

## Review

Three Fable rounds across the two stages. The first found three ways the
log could under-report (a reader that listed past its own counter
snapshot, a slow writer whose late record landed behind a client's
token, a trim that could open a hole in a delta), plus `ModifyACL`
unbracketed in both stores. The second confirmed those closed and found
the mailbox id of a SETACL coming from the registry cache instead of
from the CAS that made the change, and — in the new package —
`BlobSize` treating a missing length xattr as an error, which would have
made every blob written before this release download as a 503.

The live check found one more, after the rollout: a destroyed entry
carried the MODSEQ the messages last had rather than the one the removal
was written at, although the field is documented as the latter. Nothing
reads the field yet (no JMAP data types exist), so it is fixed in the
repository and ships with stage 2 rather than in a second rollout.

## Rollback

A pure code change: restore
`0.26.2@sha256:08673e4f3ce9f556c300ae0dc461449bbafeeffa74d58c7a48681623f160c8bd`
in both overlays and apply. The old binary ignores the `account` object
and the `len` xattr on blob chunk 0, and writes neither. The account log
then has a gap for the time it ran, which nothing depends on while JMAP
is off; a client that later reads across that gap is told to
resynchronise rather than handed a delta with a hole in it.
