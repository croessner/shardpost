# ShardPost 0.28.0: JMAP stages 2–5 in the image, bearer introspection on

Date: 2026-09-27. Status: rolled out, healthy. JMAP stays off (`jmap.addr`
is not set).

## What the release contains

Everything since 0.27.0: JMAP `Mailbox/*`, `Email/*`, `Thread/*`,
`Email/query` and `set`, push (event source, Web Push worker `shardpost
push`, `PushSubscription/*`), `Identity/*`, `EmailSubmission` through the
relay with XCLIENT, bearer logins without a user name through OIDC
introspection, identity addresses that need a local part, and the fixes of
the stage 5 review below. None of the JMAP parts is reachable while
`jmap.addr` is empty.

What changes for running users is the bearer path. Nauthilus does not
verify a token that is handed to it as a password (it treats it as an LDAP
password), so IMAP XOAUTH2/OAUTHBEARER on ShardPost could not work in
`bearer_mode: password`. The overlay now sets `bearer_mode: introspect`:
every bearer token is introspected at
`https://login.authserv.me/oidc/introspect` with the client
`shardpost-introspection` (Nauthilus v4.0.0-beta.16, allowlisted for
`roundcube-app` and the DCR profile `mail-client-v1`), and the account is
the claim `dovecot_account`. The secret comes from
`shardpost/shardpost-nauthilus-introspection`, mounted at
`/secrets/nauthilus-introspection`.

## Review

One Fable round on stage 5 (`dd69c58` … `cd38d2d`). It confirmed the Web
Push crypto against the RFC 8291 vector, the SSRF guard at dial time,
XCLIENT encoding, the send-as checks and the fail-closed bearer path, and
found one release-blocking defect:

- A user name sent with an introspected token had to equal the account
  claim literally. IMAP clients send an alias or address as often as the
  canonical account, so every such XOAUTH2 login would have failed once
  `introspect` was on. Now the name counts when it is the token's account
  or resolves to it in a lookup without a password; another account or
  none is refused, a temporary lookup failure stays temporary
  (`7287091`, with a reproducer that failed before).

Also fixed in `7287091`: `introspect` mode without `introspect_url` and an
introspection client without its secret are refused at startup; the
envelope sender must be a bare address; the push worker prunes backoff and
account checks of what a scan no longer finds; the `jmap-push` component
pinned 0.26.0, which has no `push` command.

Deferred to before JMAP goes live: the client address XCLIENT names is the
TCP peer, which behind HAProxy is the proxy (M3); verification POSTs to any
public port (L2); the verification queue is lost if the worker dies inside
`verify()` (L4); From names in charsets Go cannot decode (L5).

## The user path

An IMAP session against `shardpost:993` with the test account from
`imaptest-creds` ran LOGIN, CREATE, APPEND, SELECT, UID STORE, EXPUNGE,
CLOSE and DELETE; every command answered OK and the scratch mailbox was
removed again.

`AUTHENTICATE XOAUTH2` with an invented token answered
`[AUTHENTICATIONFAILED]`, not a temporary failure: ShardPost reached the
introspection endpoint, authenticated as `shardpost-introspection`, and got
`active:false`. A complete XOAUTH2 login with a real token needs an
interactive OIDC login with MFA and was not run.
