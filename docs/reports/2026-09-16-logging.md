# Operational logging in Kubernetes

Starting point: two healthy replicas running version 0.11.2 produced no logs
in the 30 minute window that was examined. The start of an IMAP connection,
normal logins and the end of a session had no log calls. `slog`/JSON was in place,
but with a fixed info level.

Implemented:

- Validated `logging.level`/`LOG_LEVEL`: debug, info (default), warn, error.
- Uniform session IDs and effective client/target addresses for IMAP,
  POP3, ManageSieve and LMTP; start/end including session duration at info.
- Authentication success/rejection at info, temporary faults and
  connection limits at warn; STARTTLS success at info, errors at warn.
- Known command names and runtimes at debug, unknown commands as
  UNKNOWN. No new logs of arguments, SASL data or payloads.
- User binding after a successful login; IMAP UNAUTHENTICATE removes
  it but preserves the session ID.
- The Kubernetes configuration sets LOG_LEVEL explicitly to info.

Verification:

- Race tests for config, logging, IMAP, POP3, ManageSieve passed.
- New tests check level filtering and validation, the PROXY client IP,
  the session ID across a repeated login, and the absence of secrets at debug.
- Both test accounts verified beforehand through the public director:
  TLS, IMAP/ManageSieve login, NOOP and logout successful. No
  mail deliveries, script or mailbox changes for this demonstration.

- Full Linux test suite `go test -tags tentacle ./...` passed;
  the required third_party test data was mounted read-only into the test
  container. Build and `go vet` passed.
- Local release image: `docker.io/chrroessner/imapcephpoc:0.11.3`.

Rolled out to production: `0.11.3`, digest
`sha256:b32270400f58ccb976af35d879fde7f25a78a4a53ad3bb83dab5519027d9f982`.
Both replicas are Ready, without restarts. Deployment and scrub CronJob
use the same digest; the deployment sets `LOG_LEVEL=info`. The comparison
of the pod spec shows only the image change and LOG_LEVEL.

Public demonstration after the rollout: both test accounts logged in successfully
over IMAP and ManageSieve, NOOP and logout successful. All four sessions
have coherent connection_open/auth_success/connection_close logs,
an unchanged session ID and a public effective client IP.
In the window examined: 152 info lines, no debug, warn or error lines.
The connection logs also cover the regular director health checks.

Rollback: set the deployment back to the saved 0.11.2 digest and
remove LOG_LEVEL, set the scrub CronJob back as well. The server
ConfigMap was not changed. The local release overlay contains the
new digest and the explicit info setting.

Evidence: `/private/tmp/imap-logging-linux-tests.log`,
`/private/tmp/imap-logging-build.log`. Rollback backups of the deployment
and the CronJob as well as a tightly scoped rollout script are likewise stored under
`/private/tmp/imap-logging-*`. The script checks the previous image digest
and guards the change with the current Kubernetes resourceVersion.
