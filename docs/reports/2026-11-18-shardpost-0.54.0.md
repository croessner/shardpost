# ShardPost 0.54.0: read-only MCP endpoint

Date: 2026-11-18

## Why

An operator should be able to look at ShardPost from an MCP host (Claude
Code, Codex, an own agent) without `shardpostctl`, a client certificate or
a shell on a node, the same way the Nauthilus support MCP already works.

## What changed

- `internal/mcpserver`: an optional MCP endpoint built like the one of
  Nauthilus (own listener behind a TLS proxy, stateless Streamable HTTP,
  RFC 6750/9728 challenges, failed-token and per-person bounds, body
  inspection, transport audit). Tokens are checked by RFC 7662
  introspection at Nauthilus. See [MCP endpoint](../mcp.md).
- 28 tools: the GET operations of the admin API contract with the role
  `diagnose`, served in-process through the admin API's own handler
  (`admin.Server.ServeAs`), so roles, account scope, the admin metric and
  audit line are those of `shardpostctl`.
- Configuration `mcp:` with the keys of the Nauthilus endpoint plus
  `mcp.oauth` and `mcp.principals`; durations as in Nauthilus (`15s`).
- The image build copies `api/` (the endpoint embeds the contract).
- New dependency `github.com/modelcontextprotocol/go-sdk` v1.8.0
  (MIT/Apache-2.0), vendored. No toolchain change (it needs Go 1.25).

Review: one Fable review pass; no high-severity finding, every finding
fixed (call budget held with the slot kept until the admin call returns,
dot segments refused, introspection failures logged, stricter
configuration checks, documentation). `make lint` 0 issues,
`make test-docker` green.

## Rollout (croessner-nauthilus)

- Image `docker.io/chrroessner/shardpost:0.54.0@sha256:17cafa9d7e0ce69fa7a969170ab0ec22c9cc39f0d509bf0c777193ece8cecbc1`;
  `config check` with the overlay's MCP section valid, an invalid resource
  refused.
- Nauthilus (nauthilus-tests/kubernetes): client `shardpost-mcp` owning
  `https://mail.roessner-net.de/mcp` with allowlist `rns-support-cli`,
  scope `shardpost:diagnose` and the `groups` claim for that client;
  shadow, then prod; secret handed over as
  `shardpost/shardpost-mcp-introspection`.
- Overlay: port 9097, NodePort `shardpost-mcp` 30446 with
  `externalTrafficPolicy: Local`, NetworkPolicy for lbr1/lbr2 only,
  principal group `admin` with the role `diagnose` for all accounts.
- HAProxy on lbr1/lbr2 (rns-server `services/haproxy/shardpost-mcp-route.py`):
  `mail.roessner-net.de` + `/mcp` or the RFC 9728 paths go to
  `be_shardpost_mcp`; the existing rule admits only the administrative
  networks. Zabbix maintenance 520.

## Evidence

- `GET https://mail.roessner-net.de/.well-known/oauth-protected-resource/mcp`
  → 200 with issuer `https://login.authserv.me` and scope
  `shardpost:diagnose`.
- `POST /mcp` without a token → 401 with the `resource_metadata`
  challenge; a forged token → 401, audit `invalid_token` (the
  introspection from the pods works).
- `/oidc/authorize` for `rns-support-cli` with the MCP resource reaches
  the login page; with the JMAP resource → 400 "Invalid resource".
- After the rollout: IMAP greeting through PROXY, JMAP 401, both server
  and push pods ready.
